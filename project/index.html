Project

Overview

One project, six milestones

Every student carries one Posture C project through the semester: a language model reasoning over a tested deterministic ground, in a propose, run, read, adjust loop. The ground is a solver, simulator or evaluator in your field that the agent can call and trust. The deliverable contract has six parts.

  • The agent and its wiring: harness configuration plus at least one custom tool, skill or subagent, with your ground exposed through an MCP server you author.
  • A real problem the loop solves: optimise, fit, search or design toward a target.
  • Unit tests on your ground and tools, run in CI. Unit tests only, no secrets, no live agent.
  • A local eval answering whether the loop reliably converges. It may call the model, so it runs locally and is not a CI gate.
  • A pull request submission, peer-reviewed.
  • A report: where you drew the line, model and cost choices, how you verified the code the agent wrote, failure modes, and your eval results.

Qualification

Qualifying your ground

Your ground must meet all six criteria. Each has a test you can run yourself before you ask a human.

The six qualification criteria and the test for each.
# Criterion The test you run
1 Importable in Python, and exposes a callable API Can you import it, or its Python client, and call it to get results with no GUI? Your agent reaches it through an MCP server you write, so a GUI or an opaque binary fails.
2 Free tier or open source Is it open source, or free with an exposed API? What is the licence? Open source is strongly preferred.
3 Deterministic Run the same input twice. Is the output the same? If it is stochastic, can you fix a seed to make it so?
4 Bounded and fast Does one run take seconds rather than hours? Can it run dozens of times within a lab session? The agent runs it many times in a loop.
5 Testable Can you write a pytest test with a known input and an asserted output? CI runs those tests.
6 Non-trivial enough to need reasoning, but not so hard the loop cannot progress Is there a real search, fit or design problem where the model must interpret results and adjust? If a single call to the ground gives the final answer, it is a script, not an agent. And can a reasonable loop actually make progress toward a target?

Watch criterion 6. Criterion 6 is the one most candidate grounds fail, and it fails late. A ground can pass criteria 1 to 5 on day one and only show in practice that one call gives the whole answer, or that no loop of proposing and reading makes progress. You qualify your ground against all six in Week 6.

Auto-rejected anti-patterns:

  • Posture A: the model computes the answer itself, with no deterministic ground.
  • No loop: the model calls the ground once and you are done.
  • An ungrounded agent: much orchestration, nothing deterministic and tested underneath.
  • An untrustable ground: GUI-only, non-deterministic, or not unit-testable.
  • An unbounded ground: each run so slow the loop cannot iterate within a session.
  • A ground you do not understand and cannot judge the output of.

Specification

The specification

You write docs/spec.md in Week 6 (milestone P3). It must contain:

Specification requirements.
Requirement What it is
Goal What the loop is driving toward.
Non-goals What you are deliberately not doing.
Anti-goals What would make this a failure even if it technically works. The section people skip, and the one that catches scope drift.
Boundary Where the line falls between what the model reasons about and what the ground computes.
Success criteria How an answer is checked against the spec.

The Week 6 session also lists constraints among the spec contents.

Each milestone is an artefact that either exists at the week's tag or does not; CI checks it. Week 13 has nothing due. The full list is on the schedule.

Defence

The six defence questions

These are published in Week 1. Everyone must arrive ready to answer them about their own repository.

  1. Where is the line, and why there rather than one step further in?
  2. What did your eval's negative control do, and why that one?
  3. Which constraint was binding at your best answer, and how do you know?
  4. Show a failure you found, and say how you found it.
  5. What did you delete, and why?
  6. What would you change with another month?
